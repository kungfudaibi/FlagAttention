# MSA-007 · 长 prefill 选页复用分析（MiniMax M3 稀疏注意力）

**结论：不建议做"跨 query 组复用剩余 KV 页"这类新优化；也不建议放开 page-table 门控去启用 grouped8。
在本用例上，正确的方向是继续优化 direct kernel 本身。**

证据形态：1 个 BF16 定长用例、1 个 seed、1 份随机页表、1 张卡、合成随机输入；**不是 benchmark**，
没有做决定性 A/B。下文所有"节省"都是**逻辑页负载口径**的上界（`页数 × 65536 B`），不是实测 HBM 字节。

## 2. 选页结果（真实设备）

- 每个 query 的 `real_topk = 16`，`valid_blocks` 范围 `[121, 128]`，
  16 个 topk 槽全部有效：**sentinel = 0**，越界 = 0，全 mask 页 = 0（总计 `16384` 槽）。
- **topk 顺序不是页序**：所有 1024 个 query 的前三槽恒为 `[init_block, valid_blocks-2, valid_blocks-1]`，
  原因是 init/local 页被加了 `1e30 / 1e29` 的分数偏移。这一点决定了 prefix 规则的实际行为。

### 真实 `counts`（设备输出，已逐位复核）

64 个 16-query 组的 `counts` 全部为 **3**（`{'3': 64}`），
被离线重算的公共前缀规则**逐位复现**（`counts16_match=True`）。

即：**共享前缀恰好只吃掉了 3 个强制页（init + 2 个 local），第 4 槽起各 query 选页分叉**。
这不是"前缀很长、复用很多"的场景，而是"前缀 = 强制页"的退化场景。

## 3. 主口径：8 query 一组

当前 dispatch 因 `block_table.shape[1] (128) > 2*topk (32)` 不会走 grouped8；若**只放开这一条门控**，
`grouped_query_size` 会取 8（16 分支同样被该门控挡住）。因此 8-query 是"放开页表门控"的真实落点。

| 指标 | 全量选页 | 扣掉真实前缀 3 页后 |
|---|---|---|
| 有效访问（query×page） | `16384` | `13312` |
| 物理页并集 | `9637` | `9253` |
| 可复用访问 | `6747` | `4059` |
| 复用率 | `41.18%` | `30.49%` |
| 活跃 query / 并集 | `0.106` | `0.111` |
| 平均每页被几个 query 用 | `1.700` | `1.439` |
| 逻辑负载上界 | `1024.0 MiB` | `832.0 MiB` |
| 逻辑可省上界 | `421.7 MiB` | `253.7 MiB` |

每页复用重数分布（并集内页数）：

| 重数 | 全量 | 扣前缀后 |
|---|---|---|
| 1 | 6047 | 6047 |
| 2 | 2461 | 2461 |
| 3 | 647 | 647 |
| 4 | 89 | 89 |
| 5 | 8 | 8 |
| 6 | 1 | 1 |
| 8 | 384 | 0 |

分位（重数）：全量 p50/p90/p99/max = `1/3/8/8`；
扣前缀后 = `1/2/4/6`。

注意最后一行 `8`：那是**每个 query 都选中的 init 页**（1 页被 8 个 query 共用），它已经在前缀里被处理掉了；
扣掉前缀后该行消失，剩余页的最高重数只有 `6`。

每组的剩余访问是**常数** `104`（= 13 页 × 8 query），
剩余并集中位数 `72`、范围 `61–80`。
没有任何一组的剩余并集退化成 1 页，也就是说 grouped8 的页表 dedup 在这批数据上**永远有活干**，
但同时**只能把 104 次访问压到 ~72 页**。

| 指标 | 全量 | 扣前缀后 |
|---|---|---|
| 有效访问 | `16384` | `13312` |
| 物理页并集 | `6640` | `6448` |

| 活跃 query / 并集 | `0.154` | `0.159` |
| 逻辑可省上界 | `609.0 MiB` | `429.0 MiB` |

16 组更"划算"（剩余复用率 `51.6%`、可省 `429.0 MiB`），
但 **16 分支与 8 分支被同一条 `block_table.shape[1] <= 2*topk` 门控挡住**，放开该门控也只会得到 8，不是 16。
报告 16 组是为了给出上界，不代表现成可达。

## 5. 决定性测量：现有前缀到底值不值，复用到底能不能赚

### 5.1 现有 3 页前缀是**划算**的（反直觉，但可复现）

同一份数据、同一个 kernel、同一次 launch，只把前缀状态中性化（`count=0, m=-inf, l=0, partial=0`）后再跑一遍：

| 量 | 中位数 |
|---|---|
| 前缀 kernel 本身 | `0.4240 ms` |
| direct（真实 count=3） | `5.0682 ms` |
| direct（无前缀，全 16 页） | `6.1142 ms` |
| **边际节省** | **`+1.0460 ms`** |
| **扣除前缀成本后的净收益** | **`+0.6220 ms`** |

两臂输出一致（cos `0.99991479`，max|diff| `0.000244` ≈ 1 个 BF16 ulp，
maxdiff/rms `0.021`），所以时间差是干净的边际收益，不是语义差异。

折算：`0.363 us/页`，
前缀共省 `2880` 次页加载（占全部访问的 `17.58%`，逻辑口径 `180.0 MiB`）。

**这直接回答了"要不要为了复用再花一次前缀成本"**：前缀把 3 页从 8 个 query 各加载一次变成 1 次，
省 `1.05 ms` 而只花 `0.42 ms`，净赚 `0.62 ms`；但**它已经把能共享的部分吃干净了**。

### 5.2 放开页表门控 = 明显变慢

直接调用**未修改**的 `_gqa_sparse_fwd_grouped8`（脚本内直调，不改默认 dispatch）。
注意口径：grouped8/16 是**单个 kernel 顶替整条 attention 流水线**，所以它的对手是
"前缀 + direct"合计，而不是 §5.1 里单独的 direct kernel：

| 路径 | 中位数 | 相对现网流水线 | cos vs 流水线 |
|---|---|---|---|
| **现网流水线**（前缀 + direct） | `5.4532 ms` | `1.00x` | — |
| grouped8（单 kernel） | `9.0835 ms` | **`0.60x`** | `0.999915` |
| grouped16（单 kernel） | `7.1251 ms` | `0.77x` | `0.999913` |

该流水线数值与 §5.1 分开测的 `0.4240 + 5.0682 = 5.492 ms` 相差 `0.72%`，两份产物互相印证。

grouped8 把逻辑页访问从 104 压到 ~72（`-31%`），**实测却慢 1.67 倍**。
代价不在页负载，而在：候选展平后 `8×16=128` 个候选的逐页 `for unique_index` 串行循环、
每页重算 `(topk_values == candidate)` 选行掩码、以及 `BLOCK_TOPK=16` 的掩码/规约开销；
减少的页加载抵不过这些新增的整型/掩码工作。grouped16 也慢（`0.77x`），只是没 8 那么糟 —— 
"组越大越划算"的趋势存在，但在本 shape 上两个点仍全负，且 16 这条路被门控挡死。
所以即使按最有利的 16 组口径（§4 的 `51.6%` 复用率），也**没有**一个可达的配置能跑赢现网。

### 5.3 为什么逻辑字节的减少没有变成时间

本用例 KV cache 只有 `128 页 × 65536 B = 8 MiB`（单 KV head），整份 cache 常驻 L2；
被"省掉"的页加载多数本来就是 L2 命中。所以**逻辑页负载不是这条 kernel 的瓶颈**，
继续在"少读几页"上做文章，收益上限被 L2 按住了。真正的时间在 direct kernel 的逐页 QK/softmax/PV 与访存调度上。

## 6. 结论与建议

1. **页复用（跨 query 组复用剩余 KV 页）：不建议。** 真实前缀只覆盖 3 个强制页，
   剩余部分 8-query 分组的复用率虽有 `30.5%`，但把这部分做进 kernel（grouped8）
   实测 `0.60x`，**净亏**。逻辑上能省 `253.7 MiB`，
   而这批页绝大多数已在 L2，字节口径的收益无法兑现为时间。
2. **只放开 page-table 门控：收益可疑，实测为负。** 该门控放开后只会启用 8-query 分组（16 分支被同一条件挡住），
   而 8-query 分组实测比现网 direct 慢 `1.67 倍`。
   "门控挡住了更优路径"这个假设在本用例上**不成立**。
3. **优化 direct：支持。** 现有前缀已经用 `0.42 ms` 换回 `1.05 ms`（净 `+0.62 ms`），说明"减少重复页加载"这条路
   已被现有实现吃到尽头；进一步的收益必须来自 direct kernel 自身（逐页 QK/PV 流水、页内调度、掩码开销），
   而不是再叠一层分组复用。

> 换言之：**当前设计里"前缀复用"与"direct"的分工是对的**，缺的不是又一层复用，而是 direct 本体的效率。

## 7. 证据边界（务必连同结论一起读）

- **单点证据**：1 个 BF16 shape、1 个 seed（6）、1 份随机页表、1 张 GCU5、合成随机输入；**没有真实模型 trace**。
  换个 seed 或真实负载，页表复用重数会变，`counts` 也可能不再是常数 3。
- **前缀规则被 `range(min(4, K))` 硬截断在 4 槽**。本用例真实 `counts=3 < 4`，未触顶；但"前缀最多 4 页"是结构性上限，
  不能外推成"长前缀能复用很多"。
- **`counts` 的设备校验只覆盖 16-query 分组**（64 组，逐位一致）。**8-query 的数字是离线按同一规则模拟的**，
  设备上不存在 8-query 的 `counts`；脚本里的 `counts8_emulated` 仅作诊断，不作为实测证据。
- **字节数是理想逻辑上界**：`页数 × 65536 B`，假设每页必读满、无缓存、无合并。**绝非实测 HBM 流量**，
  且有 5.3 节说明的实际反向证据（L2 命中）。
- **没有决定性 A/B benchmark**。第 5 节的数字是单进程、单次调用、7 次重复取中位数的**诊断计时**，
  不是 orchestrator 独占门控下的正式 benchmark；不能据此宣称端到端加速比。
- grouped8/grouped16 的计时是**脚本内直调未修改 kernel**得到的，默认 dispatch **未改动**，基线行为不受影响。
- 参考对照（只读、非本任务产出）：同卡历史 profile 中 full `6.905 ms`、prefix `0.318 ms`、direct `4.945 ms`；
  本次诊断 direct 中位数 `5.453 ms`、prefix `0.424 ms`，量级一致。
- **模型集成状态：未集成 / N/A。** 本任务是 kernel 级选页与复用分析，未接入任何模型或服务，无端到端指标。
