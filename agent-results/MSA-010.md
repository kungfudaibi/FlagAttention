# MSA-010：C200 长 prefill 的 K staging、器件内布局与 M=8 QK 成本拆分

- **任务**：MSA-010 — 把 C200 MiniMax M3 MSA 长 prefill 的 K staging、器件内布局与 M=8 QK 成本拆清楚
- **代码基线**：`9d11b869993958bc34f44dd72d08e557d5355b37`（`agent/enflame-msa-k-stage-vs-qk`）
- **硬件**：S60 / ZIXIAOC200（GCU300），仅 GCU 5（PCI `0000:83:00.0`），CPU 160–191
- **形状**：`PREFILL_SHAPES[6]` = B/Q/KV/Hkv/Hq `1/1024/16384/1/8`，D128，TopK16，128 token/page，seed 6
- **脚本**：`agent-results/msa010_k_stage_vs_qk.py`（`--device 5 --verify` / `--device 5 --benchmark`）
- **结果**：`--verify` 与 `--benchmark` 均 PASS；正式计时 5 轮热态交错，逐轮原始样本全部保留

---

## 0. 一句话结论

那段被笼统记作「K load + transpose + QK ≈ 0.224 ms/page（65%）」的账**是错的**：它把三件互不相同的事捆在一起，而其中真正占钱的既不是 QK、也不是 transpose 指令、更不是等 DRAM，而是 **K 在 fused KV cache 里的交错布局导致每次只读半个 cacheline 的 2:1 跨步搬运**。

把 K 半区按 `[page, h, d, pos]` 预打包一次（4 MiB，0.135 ms）之后，同一个 kernel、同一份数据、逐位相同的输出，单次 attention 从 **5.425 → 4.195 ms（−1.231 ms, 1.294×）**；叠加 MSA-009 的 early-V 后 **5.425 → 3.685 ms（−1.740 ms, 1.472×）**，整链 **6.847 → 5.059 ms（−1.788 ms, 1.353×）**。

## 1. 结论先行：三段成本的真实归属

以 stock `_gqa_sparse_fwd_direct`（13 页/程序，grid 1024）为基准，全部为同一编译族、同一页循环、同一 grid 的配对对照，热态 5 轮中位数（ms，越低越好）：

| 臂 | 含义 | 中位数 | 相对 stock |
|---|---|---:|---:|
| `stock_attn` | 出厂 sparse attention | 5.4253 | — |
| `copy` | 逐行复刻 kernel（无改动） | 5.3943 | −0.031（复刻保真，且逐位相同） |
| `k_pre` | 复刻 + 预转置表的**指针参数**（仍走原布局） | 5.3805 | −0.045 |
| `k_pre_noptr` | 去掉页表间接（`page := blk`，**数据不同**，仅计时探针） | 4.9285 | −0.497 |
| `kview_trans` | **同一份 cache**，用转置 view 直接读（去掉 `tl.trans`） | 5.3852 | −0.040 |
| `k_pre_trans` | **打包后的 K 表** + 无 `tl.trans`（逐位相同） | 4.1948 | **−1.231** |

三段成本的归属由此确定：

1. **QK 本身（M=8, N=128, K=128 单条 convgen）≈ 0.002 ms/page**，即 13 页合计 ~0.03 ms，占 per-page 预算 **不到 1%**。MSA-008 把它记成 0.6%，方向对但绝对值仍高估。
2. **`tl.trans` 指令不是成本**。`kview_trans` 已经让 TTIR 里 `tt.trans` 消失（`ttir_has_trans=False`），但 **GCUIR 页循环里依然生成一模一样的 `slice → deslice → transpose → slice` 四段式**，耗时 5.3852 vs 5.3943，**在噪声内（−0.009 ms）**。也就是说 backend 把「转置 view 的 load」重新lower成了同样的 transpose 路径——**改源码写法去 `tl.trans` 是无效优化**，这一点必须写进结论，否则会误导后续优化。
3. **真正的大头是 K 的 2:1 跨步搬运**。`kv_cache` 是 K/V 交织的 fused 布局（`[128, 1, 128, 256]`，stride `32768/32768/256/1`）：每个 token 的 K 只占 256 B，而行距是 512 B。所以任何「只取 K」的 tile 都是 **512 B pitch × 128 行 = 64 KiB 的搬运换取 32 KiB 有用数据**，over-fetch 2.0×，并且被拆成 slice/deslice/transpose/slice 四次带阻塞 `dma_wait` 的 DTE 阶段。打包成 `[page,h,d,pos]` 后，一个 K tile 是**一段连续 32768 B**，页循环里 `slice→deslice→transpose→slice` 塌缩成**一次 slice**。

### IR 证据（同一份编译产物对比）

| 臂 | hash | shared | 页循环 dma_start/wait | transpose/slice/deslice | `tops_wait_dte` |
|---|---|---:|---|---|---:|
| `stock` | `d96f6d036197` | 65536 | 3 / 12 | 1 / 3 / 1 | 26 |
| `copy` | `b4217efee032` | 65536 | 3 / 12 | 1 / 3 / 1 | 26 |
| `kview_trans` | `fe3076b89bb4` | 65536 | 3 / 12 | **1 / 3 / 1** | 26 |
| `k_pre_noptr` | `86a3440c64f1` | 65536 | 2 / 11 | 1 / 3 / 1 | 25 |
| `k_pre_trans` | `231310d62033` | **0** | 3 / **9** | **0 / 2 / 0** | **23** |

`k_pre_trans` 的 `shared` 从 65536 掉到 **0**：K tile 不再需要 staging buffer，DTE 等待从 12 降到 9。`kview_trans` 的 hash 与 stock 不同、TTIR 也确实没有 `tt.trans` 了，但 GCUIR 页循环**逐指令同构**——这正是它不提速的原因，也是「用 IR 证明 lowering 变化」这条要求的直接落点。

**因此：MSA-009/008 里「K load+transpose+QK = 0.224 ms/page」这个可加分解不成立**，`transpose_plus_kernel_delta`（+1.186 ms）里几乎全部是**布局/搬运**，不是转置，也不是 QK。

## 2. 逐页边际成本与 QK-only 微基准

13 页 vs 4 页同形状子链（同页序、同 grid、同编译产物）的斜率：

| 臂 | 边际 ms/page | 折 us/page |
|---|---:|---:|
| `copy`（出厂布局） | 0.3448 | 344.8 |
| `k_pre` | 0.3483 | 348.3 |
| `k_pre_noptr` | 0.3114 | 311.4 |
| `k_pre_trans`（打包） | **0.2576** | **257.6** |

flat QK-only 微基准（每程序 1 个 query row × N 个真实页，同样的 topk/页表/K DMA/转置/QK，输出落盘防 DCE）：

| 臂 | 4 页 | 13 页 | 斜率 us/page |
|---|---:|---:|---:|
| `shipped` | 1.0160 | 2.7070 | 187.9 |
| `pretrans` | 0.6545 | 1.5861 | 103.5 |

即：**纯 K 读取+QK 这一段，出厂布局 187.9 us/page，打包布局 103.5 us/page**。差 84.4 us/page 完全来自搬运形态，与 softmax/V/PV 无关（这两项在微基准里根本没有）。这也是「waiting / layout / QK 谁最有 headroom」的直接答案。

### 器件内复用（reuse）控制：热地址 ≠ 已在本地

同一真实页、13 次迭代、QK 数完全一致，只改 K tile 的来源：

| 臂 | 迭代内 K DMA 次数 | 中位数 ms |
|---|---:|---:|
| `distinct_pages`（13 个不同真实页） | 13 | 2.7515 |
| `hot_address`（同一页址 13 次） | **13** | 2.7487 |
| `local_tile`（循环外载入一次，13 次 convgen 复用） | **1** | 0.6657 |

`hot_address` 与 `distinct_pages` **完全等价（−0.003 ms）**，`local_tile` 省 **2.086 ms**。这严格证明了：**「地址热」不会消除任何 local 传输**，收益全部来自真正移除的 12 次 DTE。`local_tile` 与 `hot_address` 的输出**逐位相同**（`reuse_equivalence.bit_identical=True`），所以这 2.086 ms 是纯搬运，不是算法差异。注意 `local_tile` 是**诊断上限**（真实 13 页不可能共用一页），不能当作可落地优化。

## 3. 可落地优化路径：K 半区预打包

### 3.1 为什么可行

- 打包是**纯置换**：`kv_cache[..., :128].permute(0,1,3,2).contiguous()`，字节级校验 `pretransposed_bytes_match=True`。
- 成本只在 cache 更新时付一次：实测 `pack_only = 0.1348 ms`（4 MiB）。相对 q_len=1024 的单次 attention 收益 1.231 ms，**回收期 0.11 次调用**——即同一份 cache 只要被读一次以上就净赚。
- 最坏情况（每次调用都重打包）也仍然赢：`re_pack_every_call = 4.2546 ms`（stock 5.4253），**−1.171 ms**；叠加 early-V 为 3.6850（**−1.740 ms**）。
- 内存代价：+4 MiB（cache 本身 8 MiB）。

### 3.2 统一锚点（同一形状、同一次运行、热态 5 轮）

| 链 | 中位数 ms | 相对 stock |
|---|---:|---:|
| `stock_chain`（index+topk+attn） | 6.8472 | — |
| `early_v_chain`（MSA-009 候选） | 6.2898 | −0.557 (1.089×) |
| `pack_chain` | 5.6550 | −1.192 (1.211×) |
| `pack_chain_early_v` | **5.0593** | **−1.788 (1.353×)** |
| `stock_attn` | 5.4253 | — |
| `early_v_attn` | 4.8708 | −0.555 (1.114×) |
| `re_pack_every_call` | 4.2546 | −1.171 (1.275×) |
| `re_pack_every_call_early_v` | 3.6850 | −1.740 (1.472×) |

两条优化**互相独立、可叠加**：early-V 省的是 V DMA 与 QK 的重叠（−0.555 ms），打包省的是 K 搬运形态（−1.231 ms），叠加实测 −1.788 ms，与相加（−1.786）在 0.1% 内一致。

## 4. 分解对照的有效性

### 4.1 逐位相同（等价性契约，全部 PASS）

`copy`、`k_pre`、`k_pre_trans`、`kview_trans`、`kview_trans_early_v`、`copy_early_v`、`pack_plus_attn`、`pack_once_then_attn`、`pack_once_then_attn_early_v` 与 stock **max_abs = 0.000e+00，nz = 0**。

这一点很重要：`k_pre_trans` 是**逐位相同**的，所以 −1.231 ms **不是**精度换来的。

### 4.2 诊断/上界探针（明确标注，不可当优化）

| 臂 | 为什么是探针 | 用途 |
|---|---|---|
| `k_pre_noptr` | `page := blk`，读的是**不同物理数据** | 只给「页表间接」计时上界 |
| `xp_sub4` | 4 页子链 | 只做边际斜率 |
| `local_tile` | 13 次复用 1 页，真实场景不存在 | 只给「真正本地化」的上界 |
| `m1/m2/m3/m4/m5` | 分别砍掉 softmax/V/PV，输出是 checksum | 只做阶段归因 |

所有探针都验证了**输出非零且有限**（`all_ablations_live=True`，1048576/1048576 非零），排除 DCE 造成的假加速。

### 4.3 阶段归因（同一编译族、同页循环，checksum 输出）

| 臂 | 保留 | 中位数 ms | 与上一行的差 |
|---|---|---:|---:|
| `m1_k_load_only` | 仅 K DMA+读 | 3.5479 | — |
| `m2_k_load_trans` | +显式转置 | 4.8285 | **+1.281** |
| `m3_qk_only` | 改为 QK convgen | 4.1344 | −0.694 |
| `m4_qk_softmax` | +online softmax | 4.7546 | +0.620 |
| `m5_pv_reuse_k` | PV 复用已载入 K（去 V DMA） | 4.7367 | −0.018 |
| `m1t_k_load_only` | 打包布局下仅 K DMA+读 | 3.5520 | — |
| `m3t_qk_only` | 打包布局下 QK | 2.9598 | **−0.592 vs m3** |

**这些行不能直接相减**：`m2` 显式 `tl.trans` 后 lowering 变了（页循环仍是四段式但多一次 transpose），`m3` 换成 convgen 又换了一套 DTE 编排。它们只能给**方向与量级**，不能当作可加预算。真正可加的是 §2 的 13→4 页斜率（同一编译产物内部）。

## 5. 语义与正确性校验

- **FP32 参考**：按页序逐页在线 softmax，`exp2(x·log2e)`，`max/max/acc` 与 kernel 同构。stock vs FP32 `max_abs=1.449e-04`，`cos=0.99999731`（BF16 输出，符合预期）。
- **可复现性**：同输入连续两次 `bit_identical=True`。
- **early-V 语义**：与 stock **逐位相同**（MSA-009 结论在本基线复现）。
- **因果掩码（可证伪的毒化测试）**：把未来位置 K 毒化成 30000，r=0/1/512/1023 的 `changed=0`；把 q_abs 推后一位作为阳性对照，`changed=1024`。**掩码确实生效**，不是「恰好没读到」。
- **页表间接**：16/16 页 `logical != physical`，随机物理页表真的被走到。
- **QK 逐页等价**：16 个真实页，`max_abs=2.384e-06`，`cos=1.0`；翻转表的阴性对照 `max_abs=15.42` 被**检出**（说明该检查不是恒真）。
- **打包字节**：`kt` 与 `kv_cache[..., :128]` 置换后**逐字节相同**。

## 6. 测量方法与限制（必须一起读）

1. **计数器无效**。`efsmi dmon --gpm-metrics` 在本机即便跑 30×4096³ BF16 matmul（2.6 s）仍**全 0**，已用已知正样本对照确认（`counters.available=False, positive_control nonzero=0`）。因此全部结论基于**受控 event 计时**，没有使用硬件计数器。
2. **profiler 不可用**。`torch.profiler` 的 `PrivateUse1` activity 拿不到 kernel 事件（`profiler.available=False, kernel_events=0`）。故无法给出 kernel 内 time breakdown。
3. **event 开销** 中位 11.7 us，相对 5 ms 量级为 0.2%，未做扣减。
4. **诊断 vs 候选**：只有 `k_pre_trans` / `pack_*` / `early_v*` 是**候选**（逐位相同 + 未改公共入口）；`kview_trans` 是**负结果**（同样逐位相同，但无收益）；`k_pre_noptr`、`m*`、`local_tile`、`xp_sub4` 是**诊断**，已在表中标注，不得报为优化。
5. **打包路径未改公共 API**：本报告中的 `pack` 是脚本内显式构造 + 诊断 dispatch，**尚未**接入 `FLAG_ATTN_*` 开关或默认路由。落地需要在 cache 写入侧维护一份 `[page,h,d,pos]` 视图，这会动到 KV cache 的写入路径，**属于下一步工作，不在本次范围内**。
6. **单形状**。只跑 `PREFILL_SHAPES[6]`，未扫形状；短序列/小 q_len 下打包的摊销比会更差（回收期 0.11 次调用是按 q_len=1024、13 页算的）。
7. **shared 从 64 KiB 降到 0** 是打包带来的**附带**变化。它可能额外降低了 SM 占用压力，但我没有单独隔离这项（那需要另一个只改 shared 的受控实验），所以 **−1.231 ms 归因于「搬运形态」，不宣称 shared 的独立贡献**。

## 7. 回答三个问题

**Q1：waiting / layout / QK 谁最有 headroom？**
**layout（K 的串行跨步搬运形态）**。证据链：QK 单条 convgen ≈0.002 ms/page（<1%）；`hot_address` 证明等待不是地址冷热问题（−0.003 ms）；`kview_trans` 证明去掉 `tl.trans` 指令无效（−0.009 ms）；而把同一份 K 数据换个布局就拿到 −1.231 ms。QK 的 M=8 形状本身**不是**瓶颈——它在微基准里打包后只要 103.5 us/page。

**Q2：测到的上下界？**
- K 读取+QK 段：**187.9 → 103.5 us/page**（下界由打包布局给出，且已逐位验证）。
- 单页总成本：**344.8 → 257.6 us/page**（13→4 页斜率）。
- 真正器件内复用的**上界**：2.7515 → 0.6657 ms（每程序 13 次 DMA 降为 1 次），**不可落地**，仅作上限。
- 整链：6.8472 → 5.0593 ms（1.353×），其中打包贡献 −1.192、early-V 贡献 −0.557，可加。

**Q3：可复现的优化路径？**
两段，均逐位相同、互相独立：
1. **K 半区预打包**（本报告新增，主收益 −1.231 ms / 1.294×）：`[page,h,d,pos]` 一次 0.135 ms，回收期 0.11 次调用；最坏每次重打包仍 −1.171 ms。
2. **early-V DMA**（MSA-009，−0.555 ms / 1.114×），叠加后 1.353×（整链）。
