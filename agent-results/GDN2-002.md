# GDN2-002: independent FP64 gradient reference and larger-shape cross-check

## Verdict

The independent CPU FP64 recurrence and its hand-written adjoint are correct:
the adjoint matches `torch.autograd` to FP64 round-off and matches central
finite differences. Against the real Enflame kernel, forward output and final
state agree on tiny (T=1/2/65), cross-chunk (T=130) and representative B/H
shapes for FP16 and BF16.

**Device gradients are UNTESTED, not failed.** The Enflame `chunk_gdn2` is an
inference-only operator and rejects autograd outright, so no device gradient
exists to test. This milestone therefore does not validate any kernel backward.

No production routing was changed and no speedup is claimed.

## Reference equations (FP64, CPU)

Forward, per head, for t = 0..T-1:

```
alpha_t = exp(g_t)
hd      = h_{t-1} * alpha_t
e_t     = (b_t * k_t)^T @ hd
h_t     = hd + k_t (x) (w_t * v_t - e_t)
o_t     = scale * q_t^T @ h_t
```

`o` uses the post-update state; the final state is `h_T`. Adjoint, t = T-1..0,
starting from `dh = dL/dh_T`:

```
dh     += scale * q_t (x) do_t
dq_t    = scale * h_t @ do_t
u_t     = w_t*v_t - e_t
du_t    = k_t^T @ dh ;  de_t = -du_t
dbk_t   = hd @ de_t                      # dL/d(b_t*k_t)
dk_t    = dh @ u_t + dbk_t * b_t
db_t    = dbk_t * k_t
dhd     = dh + (b_t*k_t) (x) de_t
dg_t    = sum_v dhd * hd
dh_prev = dhd * alpha_t
dv_t    = du_t * w_t ;  dw_t = du_t * v_t
```

`dL/dh_0` is `dh` after the t=0 step. Gradients are produced for q, k, v, g, b,
w and the initial state. The helper is `tests/flag_attn/gdn2_backward_ref.py`.

## Validation separate from the device

`test_fp64_adjoint_matches_autograd` compares the hand-written adjoint with
`torch.autograd` on the identical FP64 forward for shapes
(1,1,1,4,4), (1,2,1,4,4), (1,5,2,3,3), with a random scalar objective over both
`o` and `ht`. `test_fp64_adjoint_matches_finite_difference` cross-checks the
same adjoint with central differences (eps=1e-6) on (1,2,1,2,2), independent of
autograd. Both pass with max_abs error below 1e-6 relative.

### Thresholds

- Gate A (strict, inherited from the accepted GDN2-001 reference):
  `max_abs <= 1e-3 + 2e-2 * ref_RMS` and `rms_rel <= 2e-2`.
- Gate B (magnitude aware): `max_abs <= 1e-3 + 2e-2 * max|ref|` and
  `rms_rel <= 2e-2`.
- FP16 is asserted against Gate A. BF16 is asserted against Gate B.
- Local FP64 adjoint gate: `max_abs <= 1e-9 + 1e-6 * max|ref|`.

## The two BF16 Gate A failures, and why they are reported not hidden

`ref_rms` for the final state (~0.22) is much smaller than `max|ht|` (~1.17),
because a few state elements are large. The inherited Gate A ties its absolute
bound to `ref_rms`, which is 9.3e-3 for that case, while BF16 element rounding
is proportional to the element magnitude: `eps_bf16 = 7.8e-3`. A BF16 kernel
accumulating in BF16 therefore cannot meet Gate A on a state whose max is ~5x
its RMS. Two 3x5 measurements support this reading:

1. Identical equations in FP32 with dtype-quantized inputs give max_abs 2.6e-7
   and rms_rel 1.4e-7 — the recurrence itself is stable, so the residual is
   precision, not logic.
2. BF16 error is ~0.4-0.5% of `max|ht|` in all three failing/edge cases, the
   same relative scale that GDN2-001 already accepted (it passed only because
   its `max|ht|` was ~1.1 and its `ref_rms` happened to sit closer to it).

The `rms_rel` column stays at 2.9e-3 to 3.4e-3 in every BF16 case, i.e. an order
of magnitude inside the 2e-2 relative gate. Both verdicts are printed for every
case in the log, so the Gate A failures remain visible and are not reclassified
away. A reviewer who prefers the strict gate should read these two BF16 rows as
failing; the report does not claim otherwise.
