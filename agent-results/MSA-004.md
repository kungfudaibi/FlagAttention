## 2. What the dispatch actually does

`src/flag_attn/runtime/backend/_enflame/msa/sparse_attn.py` picks
`GROUP_SIZE_Q` for the grouped prefill kernel. The shipped dense-pool band
(line ~786) is:

```python
if (block_size_h <= 8 and 0 < topk <= 16
        and block_table.shape[1] <= 2 * topk
        and total_q >= 16 * batch
        and triton.cdiv(total_q, 16) * num_kv_heads >= 64):
    grouped_query_size = 16
```

The opt-in experiment (`MSA002_GROUP16_EXPERIMENT`, default off, line ~797)
only relaxes the program-count threshold to 32 and adds a 512-query floor:

```python
if (_MSA002_GROUP16_EXPERIMENT and grouped_query_size != 16
        and block_size_h <= 8 and 0 < topk <= 16
        and block_table.shape[1] <= 2 * topk
        and total_q >= 512
        and total_q >= 16 * batch
        and triton.cdiv(total_q, 16) * num_kv_heads >= 32):
    grouped_query_size = 16
```

`use_grouped8` then requires `head_dim == 128` and
`max_query_len >= grouped_query_size`; otherwise `_gqa_sparse_fwd_direct` runs.
The decode branch (line ~1260) was not read, not edited, and not measured —
the decode cap-32 question is out of scope for this task.

Real launches were captured by wrapping `triton.runtime.jit.JITFunction.run` and
recording only `warmup=False` calls, so a kernel that never executed cannot be
claimed. Per case the full prefill call launches exactly three kernels:
`_index_block_score_kernel`, then `_prefill_topk_rows_enflame` (or
`_prefill_topk_reduction_enflame` for topk ≤ 4), then `_gqa_sparse_fwd_grouped8`
(or `_gqa_sparse_fwd_direct`). Both variants launched an identical score and
topk kernel with identical grids in all 39 cases; only the attention launch
differs when the gate flips.

## 4. Timing method

`agent-results/scripts/msa003_ab.py`:

* one process per A/B run, bound to `gcu:2` and `taskset -c 64-95`;
* per case: 3 warm-up calls per variant, then **3 rounds × 15 samples** per
  variant, with the order alternating A,B / B,A / A,B inside each round so
  neither variant systematically follows the other;
* timing is a full public prefill call — `minimax_m3_index_score` +
  `minimax_m3_index_topk` + `minimax_m3_sparse_attn` — bracketed by
  `torch.gcu.Event` pairs with a synchronize before `record()` and after the
  call, not a stage-only number;
* all 45 raw samples per variant are kept in the JSONL, plus the three round
  medians; the reported number is the median of all 45;
* peak memory is measured per variant with the other variant evicted first
  (`empty_cache()`), so the A and B peaks are not contaminated;
* cold start spawns a **fresh process** with the same script (`--cold-start
  A|B`) and times the first full call on the band shape S=4096, qlen=512 —
  which the gate really moves (group 8 vs 16, verified in the payload).

Reported spread is min–max of the three round medians. Round-ratio spread
(max/min over the three rounds) was ≤ 1.010 for 33 of 39 cases; the six
exceptions are noted in §5.3.

## 8. Proposed routing condition (reversible, opt-in)

The measured band supports exactly the experiment predicate, i.e. **only** the
shipped program-count threshold relaxed from 64 to 32, with a 512-query floor:

```python
use_group16 = (
    block_size_h <= 8
    and 0 < topk <= 16
    and block_table.shape[1] <= 2 * topk
    and total_q >= 512
    and total_q >= 16 * batch
    and triton.cdiv(total_q, 16) * num_kv_heads >= 32
)
```

Properties, all confirmed by the run:

* it is a strict subset of "the shipped path would pick 8", so anything the
  shipped gate already sends to 16 is untouched (q1009, kv=2/kv=4 controls);
* it never widens the pool, top-k, head or `16*batch` gates, so the pool-33,
  topk-32, group-16→4 and batch-35 controls stay on their old kernel;
* it is one boolean over existing variables, so reverting is a one-line
  change, and it ships default-off behind `MSA002_GROUP16_EXPERIMENT`;
* as with the shipped branch, the kernel that actually runs is still gated
  downstream by `head_dim == 128` and `max_query_len >= 16`, so a shape that
  passes this predicate but has a shorter longest query falls to
  `_gqa_sparse_fwd_direct` — same behaviour as the shipped gate, not a new
  edge.

Why `total_q >= 512` is in the tested condition, and what it costs: the floor
is a scope choice, not a correctness requirement. Removing it (temporary local
edit, `probe_floor.log`, reverted; source hash back to `01df27bc…`) adds only
~1.06x shapes below 512 — kv=2 at total_q=256 and kv=4 at total_q=128 — while
kv=4 at total_q=256 is already group 16 in the shipped path, so the program
threshold alone has little left to win down there. The same probe shows the one
place the floor does bite: q500 and q511 sit at 32 programs and gain 1.23x, so
a floor of 497 would capture them too. That band was **not** A/B'd end to end,
so it stays out of the proposal; the floor is at 512 because that is the
boundary that was validated here, not because 497 was measured to be worse.

Open question for review, stated rather than hidden: the three smallest gains
in the band (1.025x at S=513, 1.031x at S=512, 1.039x at S=612 — all with page
pool 4–5 and topk 16) are within a few percent of noise-prone territory. If a
conservative variant is preferred, adding `(block_table.shape[1] >= 6 or topk <= 2)`
would drop exactly those three shapes and keep the other 25 changed cases at
≥ 1.073x (the two narrow-pool topk-1/2 cases at 1.159x/1.073x survive the
`topk <= 2` clause). That narrower condition was **not** A/B'd end to end and is
therefore a suggestion, not a result. The tested condition is the one in the
code block above.

## 10. Reproducibility across the two sweeps

The final 39-case run and the earlier 29-case run (same machine, same method,
`run1_29cases.jsonl`) agree on every shared case:

* max change in speedup across the 29 shared cases: **0.0047** (q600: 1.4829 →
  1.4782);
* all 29 shared cases keep their A/B ordering and their 8→16 (or unchanged)
  dispatch;
* absolute medians move by ≤ **0.043 ms** (worst: `control_q512_s4096_g8_k32`,
  a 0.7% shift on a 6.1 ms call); the changes are of the same size as the
  round-to-round spread and never larger than 1% of the median.

So the ratios are stable across two independent multi-minute runs, not a
single lucky sweep.

## 11. Untested / out of scope

Stated plainly so nobody reads more into this than was measured:

* **Decode cap 32** — deliberately not investigated; not read, not edited, not
  measured. No decode shape is in this report.
* **Other devices** — only GCU 2 was used. GCU 6/7 were forbidden and never
  opened; the other cards' results may differ (MSA-002 measured a different
  container with different absolute latencies).
* **head_dim ≠ 128** — the grouped kernel requires 128; all cases used 128.
  Non-128 falls to `_gqa_sparse_fwd_direct` and was not measured.
* **`max_query_len` between 1 and 15** — the grouped kernel cannot run below
  the query tile; only 15 (`batch35_q15`) and 16+ were covered, and 15 stays on
  the shipped path.
* **FP8 index/KV modes** — every case is BF16. The FP8 paths have different
  score tolerances and were not A/B'd.
* **`total_q < 512` with kv > 1** — the floor probe suggests ~1.06x there but
  it was a short exploratory run with a temporary source edit, so it is
  explicitly **not** an acceptance result and not part of the proposed
  condition.
* **Very large batches** — the largest tested is batch 35 / 109 MiB peak; the
  `max_query_len >= 16` and grid-z 255 limits at much larger batch were not
  pushed.
* **Long-run stability / thermal drift** — each case is ~1 s of work; no
  hour-scale soak was run, and the host was shared (load average 27–48 from
  unrelated work) even though the pinned cores were idle.
* **The 3 small-pool gains in §5.1** — measured, but marginal (1.02–1.04x); the
  conservative `pool >= 8` variant in §8 was not A/B'd.
* **MSA-003 incident log** — not used, by instruction.
