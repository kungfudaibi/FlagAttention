The stronger check is against the independent FP64 CPU recurrence (`gla006_oracle.py`, T=64, B1/H1): BF16 relative RMS is 1.7e-3 to 2.6e-3, i.e. BF16 input-representation error, not a kernel error. FP16 vs FP64 gives 2.7e-4 worst relative RMS (input quantization dominates), and FP32 vs FP64 gives 1.2e-6, consistent with FP32 rounding.

FP32 notes, T=64 (the oracle runs):

- Real launches: `_chunk_fwd_local_state_kernel` + `_chunk_fwd_state_scan_kernel`, `_chunk_bwd_local_state_kernel` + `_chunk_bwd_state_scan_fp32_2d_group_kernel`, i.e. the non-FP32-specialized scan kernel, because `states_in_fp32=False` on the forward route.
- `tl.dot` precision: the Enflame GCU backend advertises `allowed_dot_input_precisions == ('ieee',)`. `TRITON_F32_DEFAULT=tf32` fails at compile time in `tl.dot` with `AssertionError: input_precision must be one of ('ieee',). Got tf32` (wrapped in `triton.compiler.errors.CompilationError`). This is a compiler/backend rejection, not a GCU hang or a numerical failure. FP32 therefore always executes with IEEE dot on this backend; there is no TF32 fast path to measure.
- Unset `TRITON_F32_DEFAULT` also works (the FP32 path is IEEE by default on this backend).
- The first candidate diff carried `STATE_IN_FP32=(states_in_fp32 or k.dtype == torch.float32)`. An ablation copy without that specialisation passed the same FP32 64x64 test, so the specialisation was removed; the final `chunk_h.py` differs from the baseline only in the dtype-gate refactor. This keeps the diff minimal.

## Decision

- **The FP16 whitelist is not needed for correctness.** Every tested FP16 shape outside it produced finite tensors matching the exact old tree within one FP16 ULP, with parallel launches verified in both forward and backward, at two B/T/H regimes, two gate strengths, and a non-multiple-of-64 sequence length. The whitelist is a performance gate, not a numerical one.
- **BF16 already works and needs no change.** Its existing unrestricted parallel route matched the old tree exactly on all tested shapes and stayed within expected BF16 input-quantisation error against the FP64 reference.
- **FP32 is usable only as a small-shape opt-in experiment.** It compiles and is numerically correct on K,V <= 64 with IEEE dot, but the backend rejects TF32 outright, there is no evidence for larger shapes, and FP32 doubles both local-state memory and dot cost. Do not route FP32 in production.
- **Performance case for reviewed FP16 expansion.** Excluding the 64x64 control (~1.03x, as expected), full-call gains were 2.6x-9.3x and per-stage state-kernel gains 9.6x-79x on the tested shapes, with the largest absolute wins at 256x64 and 64x256. This is a steady-state comparison of state kernels, not a claim about end-to-end model throughput.
- **Default dispatch deliberately unchanged.** `FLAGGEMS_ENFLAME_GLA_EXPERIMENTAL_FP16_STATE` and `..._FP32_STATE` both default to 0; the legacy `EXPERIMENTAL_FP16_PARALLEL_STATE_SHAPES` set is untouched. Widening the production gate needs separate review. No PR, merge, or push was performed.

## Remaining work for a follow-up

1. Extend FP16 coverage to K or V > 256 and to larger B/T/H, where local-state memory grows as `B * ceil(T/64) * H * K * V * 4`.
2. Exercise the backward `states_in_fp32=False` scan and the `split_size > chunk_size` path with the opt-in flag, since autograd currently always requests FP32 states.
3. Check varlen and `state_v_first` only if those routes are ever meant to use the parallel kernels (today they correctly fall back).
4. If FP32 is ever wanted beyond smoke tests, re-check whether a GCU backend update adds a non-IEEE dot precision and measure it; do not fake a TF32 path.
5. Re-run the 64x64 control A/B on a quiet host to confirm it stays ~1x; treat full-call ratios as directional.
