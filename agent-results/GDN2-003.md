# GDN2-003：燧原 S60 设备前向的形状自适应 tile 优化

## 结论（Verdict）

在容器 GCU 0（PCI `23:00.0`，CPU `0-31`）上，我把两个融合 kernel 的 tile 从
“固定 256”改为“按本次调用的 K/V 实际长度取 2 的幂并夹到 `[64, 256]`”。这是
**唯一**一项改动，只改 launch 几何，不改算法、不改数值。

对精确旧提交 `a16751119704c9b6688db3a537b9156bddaa1e4a` 做交替 3 轮完整前向
A/B（每轮独立进程 + 独立 Triton cache，冷编译单独计时）：

- BF16 五个形状 geomean **1.174x**；去掉 K=V=256 对照形状后 **1.240x**。
- 单形状最大增益 **1.345x**（`(1,4096,16,64,64)`，4.1608 → 3.0926 ms）。
- FP16 两个形状 geomean **1.180x**，与 BF16 同量级，说明收益来自 tile 形状而非 dtype。
- K=V=256 对照形状 tile 本来就等于 256，实现上等价于旧路径：3 轮 0.945x，
  再补 5 轮共 8 次配对后 **0.986x（-1.4%，落在 8% 的轮间噪声内）**，判定为中性。
- 输出与 final state 与旧提交**逐位相同**（`torch.equal`，maxdiff = 0.0），
  因此数值门槛结论与改动前完全一致：`o` 全部 Gate A/B PASS，final state 全部
  Gate B PASS。Gate A 只在 BF16 的 final state 上 FAIL（测试套件 2 例 +
  A/B 7 个形状中的 3 例），且改动前后数值一模一样，属既有 dtype 精度问题。
- 显存、冷编译时间、kernel 数量、kernel 路径均无回退。

**建议：继续（保留该改动）。** 未测范围见文末；设备反向仍未验证，本任务不涉及。

## 现有正确性复验与两个 BF16 final-state 门槛

先跑基线（未打补丁的 `a167511…`）现有套件，`agent-results/GDN2-003-correctness-baseline.log`：

```
94 passed, 1 skipped, 1 warning in 212.66s
EXIT:0
```

（`tests/flag_attn/test_gdn2.py` 77 例 + `test_gdn2_backward_reference.py` 17 passed/1 skipped。）

两个门槛的定义（`test_gdn2.py` 内的判定）：

- **Gate A（旧严格门槛）**：`max_abs <= 1e-3 + 2e-2 * ref_rms` 且 `rms_rel <= 2e-2`
- **Gate B（幅值门槛）**：`max_abs <= 1e-3 + 2e-2 * ref_max` 且 `rms_rel <= 2e-2`

BF16 只有两例 Gate A FAIL，两例都 **Gate B PASS**，且都在 `ht`（final state）上，
`o` 全部通过：

| 用例 | 量 | max_abs | rms_rel | ref_rms | ref_max | Gate A | Gate B |
|---|---|---|---|---|---|---|---|
| `T=130 bf16 B2 H3 K64 V64` | ht | 5.897e-03 | 3.435e-03 | 2.212e-01 | 1.170e+00 | FAIL | PASS |
| `T=65 bf16 B2 H2 K128 V128` | ht | 4.407e-03 | 2.906e-03 | 1.622e-01 | 8.801e-01 | FAIL | PASS |

原因不是 kernel 缺陷，而是 Gate A 用 `ref_rms` 做尺度：final state 的元素幅值远大于
其 RMS（`ref_max/ref_rms` 分别为 5.3 和 5.4），BF16 只有 8 位尾数，单个大元素的
量化步长就已经超过 `2e-2*ref_rms`。FP16 同样输入下 `rms_rel` 为 4.3e-04 / 4.1e-04，
比 BF16 小 7 倍，Gate A 全 PASS —— 这是 dtype 精度差异，不是实现差异。

补丁后重跑同一套件（`agent-results/GDN2-003-tests-patched.log`）：

```

EXIT:0
```

109 = 77（`test_gdn2.py`）+ 17（backward reference）+ 15（本任务新增 tile 测试）。
两个 Gate A FAIL 与基线**逐位相同**（同样是 5.897e-03 / 4.407e-03），因为改动后

## 瓶颈定位（≥3 个 T / 状态维度）

同步事件计时，`TOPS_VISIBLE_DEVICES=0 taskset -c 0-31`，BF16，seed 42，
`chunk_size=64`。每次调用只启动两个 Triton kernel：

- **K1** `_chunk_gdn2_fwd_intra_infer_kernel`：chunk 内 WY / score 预计算
- **K2** `_chunk_gdn2_fwd_h_o_infer_kernel`：按 chunk 串行推进状态并输出

`agent-results/GDN2-003-profile.jsonl`（自适应 tile，稳态中位数）：

| shape (B,T,H,K,V) | K1 ms | K2 ms | 完整调用 ms | 峰值分配 MiB | 中间量 MiB |
|---|---|---|---|---|---|
| (2, 512, 8, 64, 64) | 0.395 | 0.420 | 0.788 | 18.5 | 8 |
| (1, 2048, 8, 64, 64) | 0.628 | 0.695 | 1.225 | 36.25 | 16 |
| (1, 4096, 16, 64, 64) | 2.138 | 1.187 | 3.071 | 144.5 | 64 |
| (2, 2048, 4, 128, 128) | 0.737 | 0.911 | 1.523 | 65.0 | 28 |
| (1, 1024, 4, 256, 256) | 0.344 | 0.923 | 1.185 | 32.0 | 13 |

改动前（固定 256 tile）的完整调用中位数，同样本口径：
0.892 / 1.565 / 4.139 / 1.787 / 1.239 ms（顺序同上表），其中
`(1,4096,16,64,64)` 的分阶段为 K1 3.147 + K2 1.544 ms。与上表对照可见：
T 越长 K1 越主导（该形状 K1 占基线的 67%，占优化后的 64%）；短序列两段大致各半。

读法（注意各形状的 B/T/H 不同，下表只做同形状内部与跨形状的定性归因，
不做跨形状的线性缩放推导）：

1. **T / 序列长度**：`(1,4096,16,64,64)` 的 K1 2.14 ms 是五者最大，且它同时是
   T 最长、H 最多的形状；K1 的 grid 覆盖 `NT × BH`，随 T 与 H 一起涨。
   K2 按 chunk 串行、按 V tile 与 BH 并行，对 T 的敏感度低于 K1（该形状
   K2 1.19 ms < K1 2.14 ms）。**长序列的首要开销是 K1。**
2. **K/V（dot 宽度）**：五者的 K1 在 0.34–2.14 ms、K2 在 0.42–1.19 ms 之间。
   把 256 宽 tile 用在 K=V=64 上时（旧路径），K1/K2 都要发 256 宽的 dot；
   改成 64 后同形状直接省掉 3/4 的 lane —— 这才是 1.12x–1.35x 的来源。
   `(1,1024,4,256,256)` 的 K1 只有 0.34 ms 却 K2 0.92 ms，说明 K=V=256 时
   瓶颈已转移到 K2 的状态推进与输出，此时 tile 夹取无从下手（也是它中性的原因）。
3. **状态维度**：`h` 为 `B*H*K*V`，`(2,2048,4,128,128)` 的 `h` 为 32.5 MiB、
   峰值 65 MiB；`(1,1024,4,256,256)` 的 `h` 只有 16 MiB，反而更慢在 K2 上。
   **状态大小本身不是瓶颈，dot 宽度与 chunk 串行深度才是**，这也排除了
   “省显存带宽”这一类解释，与“tile 夹取只减少被 mask 的 lane”一致。

决定性的证据来自 launch 记录：改动前每个形状的 tile 都是

```
intra: BK=256 BV=256        (K, V 实际可能是 64 或 128)
h_o  : BK=64/128/256 BV=256 (BK 已按 K 自适应，BV 仍是 256)
```

也就是说 `K=64` 时 intra 的 256 宽 dot 有 192 条 lane 被 mask 掉，`V=64` 时两个
kernel 各有 192 条 V lane 被白算。两个 kernel 都用带边界检查的 block pointer 访问
tile，因此**把 tile 夹到真实长度不改变任何一个元素的累加顺序**——这正是后面能拿到
逐位相同输出的原因。

## 唯一一项局部优化

`src/flag_attn/runtime/backend/_enflame/FLA/gdn2/chunk_gdn2.py`，+33 −3：

```python
_S60_TILE_MIN = 64
_S60_TILE_MAX = 256
_S60_TILES_ADAPT = os.environ.get("FLAG_ATTN_GDN2_FIXED_TILES", "0") != "1"

def _s60_tile(extent: int, limit: int) -> int:
    if not _S60_TILES_ADAPT:
        return limit
    tile = _S60_TILE_MIN
    while tile < extent and tile < limit:
        tile *= 2
    return min(limit, max(_S60_TILE_MIN, tile))
```

调用点只有三处：

```python
intra_bk = _s60_tile(K, _S60_INTRA_BK)     # BK=intra_bk
intra_bv = _s60_tile(V, _S60_INTRA_BV)     # BV=intra_bv
state_bv = _s60_tile(V, _S60_STATE_BV)     # BV=state_bv
```

`_S60_STATE_BK_*` 原本就按 K 分档（64/128/256），未改。取 2 的幂是为了保持 S60 的
dot 形状对齐；下限 64 避免产生过窄的 tile；上限沿用调优过的 256。
`FLAG_ATTN_GDN2_FIXED_TILES=1` 精确恢复旧行为。A/B 的 legacy 侧**同时**满足两个
条件：源码取自旧提交 `a167511…` 的 `git archive`，且注入该环境变量 —— 这样即使
旧树里没有这个开关也不会失效，两侧因此是“同一份算子语义、同一套输入、同一张卡”，
只差 tile 选择本身。

数值中性验证（`agent-results/GDN2-003-bitidentity.log`）：同一进程内切换
`_S60_TILES_ADAPT` True/False，5 个 BF16 形状 + 2 个 FP16 形状，`o` 与 `ht`
**全部 `torch.equal`，maxdiff 0.0**，`ALL_EQUAL True`。

## A/B 方法与可复现性

`benchmark/gdn2_forward_ab.py` 有两个子命令：

- `drive`：用 `git archive` 从两个不可变提交各取一份树（旧
  `a167511…`、新 `HEAD`），对每个 (轮次, 变体, dtype, 形状) 起**独立子进程**并给
  独立 `TRITON_CACHE_DIR`，交替顺序（奇数轮 legacy→adaptive，偶数轮反向）。
- `run`：单边测量。子进程内先做 1 次计时调用得到 `cold_compile_s`（含 JIT 编译），
  再做 ≥3 s 的时钟预热（`clock_warmup_iters` 记录实际次数），最后用 `torch.gcu.Event`
  逐次同步采 15 个稳态样本。

固定条件：`TOPS_VISIBLE_DEVICES=0`、`taskset -c 0-31`、`chunk_size=64`、seed 42、
同一份输入构造代码。legacy 侧额外注入 `FLAG_ATTN_GDN2_FIXED_TILES=1`。

为什么必须做时钟预热：冷进程第一次采样会拿到未升频的时钟。实测同一形状
（`(2,512,8,64,64)`，BF16）不预热时中位数 5.92 ms，升频后 0.74 ms，
差 8 倍；不预热会把“升频”误记成 kernel 变慢。预热循环与采样循环分开计时，
预热耗时不计入任何统计量。

机器状态：A/B 期间宿主 `loadavg(1)` 在 30–63 之间波动（同容器还有其它任务），
因此每轮都记录了 `loadavg`、`efsmi` 已用显存与逐次样本；结论只依据**同一轮内
相邻的 legacy/adaptive 配对**和 3 轮配对的一致性，不依据跨轮绝对值。

复现命令（在克隆根目录）：

```bash

TOPS_VISIBLE_DEVICES=0 taskset -c 0-31 /flagos/bin/python \
    benchmark/gdn2_forward_ab.py drive \
    --old-ref a16751119704c9b6688db3a537b9156bddaa1e4a --new-ref HEAD \
    --rounds 3 --dtypes bfloat16 float16 \
    --out agent-results/GDN2-003-ab.jsonl
python3 benchmark/gdn2_forward_ab_summarize.py agent-results/GDN2-003-ab.jsonl --dtype bfloat16
python3 benchmark/gdn2_forward_ab_summarize.py agent-results/GDN2-003-ab.jsonl --dtype float16
```

耗时约 15 min。`drive` 的退出码 = 任一子进程非 0 则 1，否则 0。

- 峰值分配（`max_memory_allocated` 增量）：9.25 / 18.125 / 72.25 / 32.5 / 16.0 MiB

- 数值门槛：`o` 的 Gate A/B 42/42 全 PASS；`ht` 的 Gate B 42/42 全 PASS。

- **设备反向**：`chunk_gdn2` 是 inference-only，autograd 下直接抛
  `RuntimeError: chunk_gdn2 is inference-only`。本任务的任何数据都不是设备反向验证，
  也不能用 CPU FP64 参考代替。设备梯度状态仍为 **UNTESTED**。

- `chunk_size != 64`（K2 对 `BT != 64` 直接拒绝）。
- K/V 不是 2 的幂、或 K/V > 256、或 K ≠ V 的形状；B/H 超出采样的 1–2 / 4–16。
- 其它 dtype（FP32、FP8）与其它 GCU 型号/卡数（只测了单卡 GCU 0）。

## 停止/继续建议

**继续。** 理由：

1. 增益稳定且可解释：5 个受影响的形状三轮同向，1.12x–1.35x，远超 5–7% 的噪声地板；
   FP16 独立复现了同一量级，说明机制是 tile 宽度而非 dtype 偶然。
2. 零数值代价：输出与 final state 与旧提交逐位相同，正确性套件从 94 通过变为
   109 通过（新增 15 例），两个已知 BF16 Gate A FAIL 原样保留、Gate B 全 PASS。
3. 零资源代价：显存、kernel 数量、冷编译时间均无回退；K=V=256 为中性对照。
4. 风险可控：单一开关 `FLAG_ATTN_GDN2_FIXED_TILES=1` 可一键回退，
   `_s60_tile` 是纯函数且有 11 例单测覆盖。

后续若要继续推进，建议顺序：先补 K ≠ V 与非 2 的幂 K/V 的形状测试（`_s60_tile`
会向上取整，需确认 mask 行为），再评估把 `_S60_STATE_BK_*` 的三档常量也并入同一
夹取函数（本次刻意未动，以保持“只做一项优化”）；设备反向在算子支持 autograd 之前
不应纳入任何性能结论。
