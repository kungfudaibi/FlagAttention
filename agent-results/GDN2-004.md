# GDN2-004：不规则状态维度与第二处前向 tile 优化

## 结论（Verdict）

在容器 GCU 0（PCI `23:00.0`，CPU `0-31`）上，以已接受的 GDN2-003 提交
`c2f42ac07fc15e96f748e1a819fb32a554b11911` 为基线，本任务做两件事：

1. **验证不规则维度**（K≠V、非 2 的幂）：实测支持范围是 `K <= 256`、`V` 无上限，
   K>256 由**基线已有**的显式 `ValueError` 拒绝。20 个边界形状中 **16 个成功执行**
   且全部有限、输出/最终状态形状正确、通过严格 Gate A；另 4 个因上述基线检查被
   明确拒绝（不是崩溃，也不是新回退）。
2. **一处可回退的前向优化**：K2（`chunk_gdn2_fwd_h_o_infer`）在 `128 < V <= 256`
   时把 state V tile 拆成两个（BV=256 → 128），让该 kernel 的并行度从
   `(1 个 V tile) × (B·H)` 提升到 `2 × (B·H)`。

**state BK 三档选择经实测没有可靠收益，因此没有改动**（见第 4 节）：把
K∈(128,256] 的 BK 从 256 降到 128，在 tile 真正变化的 4 个形状上一致**变慢
0.89–0.93x**（12/12 轮），且因为 K 是 readout 的累加轴而**不再逐位相同**；
保留三档是正确选择。

对精确基线提交做交替 3 轮完整前向 A/B（每轮独立进程 + 独立 Triton cache）：

- 规则真正生效（`128 < V <= 256`）的 5 个形状，合并两轮 A/B 共 25 次配对，
  **中位 1.070x、geomean 1.075x、23/25 次 >1，符号检验 p≈1e-5**。
- 规则不生效的 7 个对照形状合并 31 次配对：**中位 0.999x、geomean 1.005x**，
  即中性——说明增益确实来自 V tile 拆分，而不是测量偏差。
- 输出与 final state 与基线**逐位相同**（SHA-256 相同），故数值门槛结论与改动前
  完全一致：`o` 全部 Gate A/B PASS；BF16 的 `ht` 有 5/8 个形状 Gate A FAIL、Gate B
  全 PASS，属**基线既有** dtype 精度问题（改动前后一模一样）。
- 峰值显存逐形状完全相同；冷编译时间两侧同量级（中位 15.2–17.2 s）无回退；
  kernel 路径不变（仍是 K1+K2 两个 kernel），唯一变化是 K2 的 BV。

**建议：继续（保留该改动）。** 但增益是中等量级（约 1.07x），不是 GDN2-003 那种
1.2x 级别，且完全局限于 `128 < V <= 256`；默认生产路由未改。未测范围见文末；
**设备反向仍未验证**，本任务不涉及反向。

## 3. 改动内容与 kill switch 修正

优化本体（`513a0e8`）：`_s60_state_bv(V)` 在 `128 < V <= 256` 时返回 128，否则走
GDN2-003 的自适应 clamp。**V 不是任何累加轴**（state 更新 `kg^T @ v_new` 与 readout
`qg @ h` 都只对 K 和 chunk 归约），所以拆 V 只改 launch 几何，结果应逐位相同——
这一点在 A/B 中由 12/12 形状的 SHA-256 相等直接证实。

`b77207f` 修正了一个真实缺陷：kill switch 关闭时原实现返回**一律 256**，
而 GDN2-003 的规则是"clamp 到实际 V"。两者在 V≤128 时不同（例如 V=96：
GDN2-003 是 128，一律 256 是 256），因此"回退开关"并没有回到被接受的基线行为，
A/B 的基线侧也会被悄悄换成另一种 tile。修正后关闭开关精确等于 GDN2-003 规则：

```python
def _s60_state_bv(extent: int) -> int:
    if not _S60_TILES_ADAPT or not _S60_STATE_BV_SPLIT_ENABLED:
        return _s60_tile(extent, _S60_STATE_BV)   # == GDN2-003
    limit = _S60_STATE_BV_SPLIT if extent <= _S60_STATE_BV else _S60_STATE_BV
    return _s60_tile(extent, limit)
```

已核对：默认路径下 `513a0e8` 与 `5f14f43` 的 12 个 A/B 形状输出 SHA **完全相同**，
所以这次修正不改变候选的默认行为，只让回退开关名副其实。

## 4. state BK 三档分析（结论：不改）

`chunk_gdn2_fwd_h_o_infer` 的规则是 `K<=64 → BK=64`、`K<=128 → BK=128`、否则 256。
任务要求分析这条规则。用 `benchmark/gdn2_state_bk_probe.py` 在同一进程内**交替**
比较"出厂三档"与"K∈(128,256] 强制 BK=128"，3 轮，原始记录
`agent-results/GDN2-004-state-bk.jsonl`：

| shape | 出厂 K2 BK/BV | 强制 K2 BK/BV | 出厂 K2 ms | 强制 K2 ms | 比值 | 逐位相同 |
|---|---|---|---|---|---|---|
| (2,512,4,96,96) | 128/128 | 128/128 | 0.4785 | 0.4920 | 0.973 | True（tile 未变） |
| (2,512,4,96,160) | 128/128 | 128/128 | 0.5626 | 0.5203 | 1.081 | True（tile 未变） |
| (2,512,4,160,160) | 256/128 | 128/128 | 0.6140 | 0.6693 | **0.917** | False |
| (2,512,4,192,192) | 256/128 | 128/128 | 0.6783 | 0.7348 | **0.923** | False |
| (1,1024,4,256,256) | 256/128 | 128/128 | 0.8323 | 0.9283 | **0.897** | False |
| (2,512,4,160,96) | 256/128 | 128/128 | 0.5880 | 0.6494 | **0.906** | False |

要点：

1. 在 **K∈(128,256] 的 4 个形状上，强制 BK=128 一致变慢**（K2 阶段 0.89–0.93x，
   12/12 轮全部 <1，最慢 0.886、最快 0.926）。K 略大于 128 时用 256 宽 dot 虽然有
   一半 lane 被屏蔽，但换来更少的 K 分片（K=160 只需 1 片而不是 2 片），实际更快。
2. BK 与 BV 不同：**K 是 readout 的累加轴**，改 BK 会改变归约分组，输出**不再逐位
   相同**（表中 `False`）。因此即使更快也需要重新论证数值门槛，而它并没有更快。
3. K≤128 的两例 tile 本来就等于 128，"强制 128"是同一配置，比值 0.97/1.08 只是噪声，
   `bit_identical=True` 也证明配置未变。
4. 结论：**保留三档规则，不做改动**。这是"该方向没有可靠收益"的情形，按任务卡
   记录理由即可，不需要为了"做了一处优化"而改它。第二处优化名额已用于 V tile 拆分。

## 5. 正式 A/B

### 方法

- 两侧都从**不可变提交**用 `git archive` 导出到 `/tmp`，不共享工作树。
- 基线侧注入 `FLAG_ATTN_GDN2_STATE_BV_SPLIT=0`（并在 `5f14f43` 之后精确等于
  GDN2-003 规则）；候选侧用默认（拆分开启）。
- 每个 (round, variant, dtype, shape) 一个**独立进程** + 独立 `TRITON_CACHE_DIR`，
  所以"冷编译"是真的首次编译。
- 记录冷编译后再做 3 s 时钟预热 + 5 次 warmup，然后用同步 `torch.gcu.Event`
  采 **15 个稳态样本**；冷编译与稳态分开记录。
- 交替顺序：奇数轮 base→cand，偶数轮 cand→base。
- 每个样本记录 `o`/`ht` 的 SHA-256、有限性、对 CPU FP64 递推参考的
  `max_abs`/`rms_rel`/`ref_rms`/`ref_max`、峰值分配、launched kernel 的
  name/grid/BK/BV/BT/num_warps/num_stages。

复现命令（克隆根目录）：

```bash
TOPS_VISIBLE_DEVICES=0 taskset -c 0-31 /flagos/bin/python \
    benchmark/gdn2_forward_ab_004.py drive --workspace . \
    --base-ref c2f42ac07fc15e96f748e1a819fb32a554b11911 --cand-ref HEAD \
    --rounds 3 --out agent-results/GDN2-004-ab-final.jsonl
TOPS_VISIBLE_DEVICES=0 taskset -c 0-31 /flagos/bin/python \
    benchmark/gdn2_forward_ab_004.py check --out agent-results/GDN2-004-ab-final.jsonl
```

任务配置里 benchmark 命令是**无参数**的 `/flagos/bin/python benchmark/gdn2_forward_ab_004.py`；
脚本现在把这等价于 `drive --out agent-results/GDN2-004-repro.jsonl`
（完整 3 轮 A/B，同一套断言，失败非零退出），因此那条命令也可直接复现。

同一形状同一侧的 3 轮中位数 max/min：**中位 1.063，最差 1.103**（BF16 与 FP16 合并，

## 9. 建议（继续 / 停止）

**继续**，保留 `128 < V <= 256` 的 K2 V tile 拆分；**不改**默认生产路由
（本改动只是把已有默认值背后的规则修正为可回退且与 GDN2-003 一致，路由本身未变）。

依据：

- 规则生效的 5 个形状合并 25 次配对：中位 1.070x、geomean 1.075x、23/25 同向、
  符号检验 p≈1e-5；对照 31 次配对中位 0.999x（中性）。增益真实但幅度中等。
- 输出与 final state 逐位相同（12/12 形状 SHA 相等），因此不存在数值回退。
- 峰值显存完全相同，冷编译无回退，kernel 路径不变。
- state BK 三档经实测更优，**不改**是正确的；该方向没有可靠收益，已记录理由。

若要继续提升 (128,256] 区间，下一步应优先考虑 K2 的 chunk 串行轴（例如把 chunk
再分段做并行前缀），而不是继续动 BK/BV——后者已到本形状集合的局部最优。
任何此类改动都必须重新验证数值门槛，因为 chunk 轴是状态递推的累加轴。

**明确的停止条件**（本次未触发）：若合并中位加速低于噪声地板（约 1.06x）、
或任一形状的 SHA/门槛判定与基线不同、或峰值显存/冷编译出现回退，则应停止并回滚。
本次三条均未触发；唯一需要注意的是增益幅度仅略高于地板，因此结论依赖合并统计，
不依赖任何单轮数字。
