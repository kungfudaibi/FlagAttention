## 2. Real call path and actual kernels

The Enflame backend overrides both MSA operators, so the generic CUDA kernels in
`src/flag_attn/minimax_sparse_attention/` are **not** what runs here. Actual
launches captured by intercepting `JITFunction.run` (`warmup=False`):

Prefill `[B,Q,S,KVH,H]=[1,512,4096,1,8]`, topk=16, init/local=1/2:

| Stage | Entry | Kernel (module `runtime/backend/_enflame/msa/`) | Grid |
|---|---|---|---|
| score | `minimax_m3_index_score` | `_index_block_score_kernel` (portable, Enflame launch) | (8,1) |
| topk | `minimax_m3_index_topk` | `_prefill_topk_rows_enflame` | (64,1,1) |
| attention | `minimax_m3_sparse_attn` | `_gqa_sparse_fwd_grouped8`, `GROUP_SIZE_Q=8` | (64,1,1) |

Decode `[1,1,16384,1,8]`, topk=16:

| Stage | Entry | Kernel | Grid |
|---|---|---|---|
| index score | `minimax_m3_index_decode` | `_decode_index_score_kernel_enflame` | (1,128,1) |
| index topk | same | `_decode_topk_rows_enflame` | (1,1) |
| attention | `minimax_m3_sparse_attn_decode` | `_gqa_sparse_decode_kernel_enflame` | (16,1) |
| attention merge | same | `_merge_topk_attn_out_kernel_enflame` | (1,8) |

Path switches confirmed by launch capture:

- prefill topk: `_prefill_topk_rows_enflame` for streaming-eligible rows;
  `_prefill_topk_reduction_enflame` otherwise.
- prefill attention: `_gqa_sparse_fwd_grouped8` when
  `head_dim==128 and max_query_len>=group and block_table.shape[1]<=2*topk`;
  otherwise `_gqa_sparse_fwd_direct`. At S=16384 the pool gate fails
  (`128 > 2*16`), so **S=16384 runs `_gqa_sparse_fwd_direct`** — this was
  verified by the empty grouped8 capture, and is why the group-size change is
  correctly a no-op there.
- decode index: `max_block<=topk` uses `_decode_topk_identity_enflame` (e.g.
  S=2048: 16 pages <= topk=16 -> 1 kernel, no score kernel). S>=4096 uses
  score + rows topk (2 kernels).
- decode attention: `total_q*num_kv_heads=8 < 512`, so `direct_output` is False
  and the state is split into chunks=2 -> decode kernel + merge kernel.

No fallback kernel was used for any reported number.

## 5. Profiler limitation (explicit)

`torch.profiler` in this image **does not attribute device kernel time**:

- `ProfilerActivity.GCU` and `PrivateUse1` produce **0 events**.
- `ProfilerActivity.CPU` (and CPU+PrivateUse1) produces host events only:
  `device_time_total == 0` for every row, no `kernel` category in the chrome
  trace, no Memcpy rows.
- `torch.profiler` is therefore used here **only** for host-side launch
  accounting, which was obtained more reliably by intercepting
  `JITFunction.run`. Missing device events were **not** interpreted as zero
  kernel time.

Log: `prof_probe.log`.

## 6. Primary bottleneck evidence

**Prefill is the dominant cost and its bottleneck is the prefill attention
kernel, specifically the page-grouped kernel's CTA/M-tile shape at 2
multi-processors.**

Evidence:

1. Attention is 1.8887 of 2.2367 ms whole-call = **84.4%**. Score 9.9%,
   topk 10.1% (stage-only; they do not sum to the whole).
2. Prefill attention is strongly sublinear in Q (0.70 -> 1.32 -> 1.89 -> 2.09 ms
   for Q=128/256/512/1024), so between 128 and 1024 queries it is limited by
   CTA count / tile efficiency, not by arithmetic volume.
3. The kernel processes a group of `GROUP_SIZE_Q` adjacent queries over the
   **union** of their selected pages. Measured union for the shipped 16-query
   group: mean 30.5 pages vs 16 selected per query -> 1.91x redundant page
   coverage per group; each CTA re-loads the whole union.
4. The shipped dispatch requires `cdiv(total_q,16)*num_kv_heads >= 64` before it
   will use the 16-query group. On this 2-multi-processor part, Q=512/S=4096
   therefore falls back to `GROUP_SIZE_Q=8` (64 CTAs of M=64) even though 32
   CTAs of M=128 are faster.
5. Alternating A/B at identical inputs (section 7) shows the 16-query group is
   **1.23-1.55x** faster in exactly the band the shipped gate excludes, and
   exactly 1.00x where the gate already chooses 16 — i.e. the effect is caused
   by the dispatch decision, not by drift. In the quiet window the same ratios
   reproduced to three decimals (1.229x / 1.550x / 1.549x), so this is the
   primary actionable bottleneck.

**Decode is launch/latency bound, not throughput bound.** Index is 0.1615 of
0.1989 ms whole (81%); de-amortized it is 0.094 ms with ~0.069 ms fixed cost
per call. Attention is ~0.119 ms and flat in S, consistent with a fixed 16-page
top-k. Decode index also grows with visible pages because the score kernel
launches one CTA per 128-token page (`num_kv_chunks = min(128, max_block)`);
that is a second, smaller opportunity (section 7.4): at S=16384 the score kernel
goes 0.1035 -> 0.0739 ms at 32 chunks (**1.40x**), bit-exact, but the whole
decode call only improves ~1% because fixed per-call cost dominates at batch 1.
`num_kv_chunks=512` exceeds the `grid.y <= 255` hard limit.

## 7. Phase 3 optimization: relaxed group-16 gate (default off)

### 7.1 Hypothesis

Increase `GROUP_SIZE_Q` from 8 to 16 for small-pool prefill with
`total_q >= 512` and `cdiv(total_q,16)*num_kv_heads >= 32` (instead of 64).
Concretely: halve the CTA count, double the M tile (64 -> 128 rows), halve the
per-group KV loads, at the cost of a slightly larger page union (30.25 -> 30.5
pages, essentially unchanged) and lower grid parallelism.

Correctness risk: the grouped kernel masks each query's own selected pages
(`selected_q` / `qk_mask_flat`) so union membership must not change results
beyond BF16 rounding; causal and prefix masking are per-row. Risk is highest for
ragged batches where `group_start >= q_len` early-exits.

### 7.2 Implementation

Two independent, separately scoped switches, both **default off** (env var
unset/`0` reproduces the exact old launch decisions). The old code paths are
untouched; each new `if` only runs when its switch is on, and each module flag
can also be toggled in-process for A/B.

### 7.4 Second hypothesis: decode index-score chunk cap (default off)

Shipped decode launches the score kernel with `num_kv_chunks =
min(128, max_block, 512//batch)`. For qlen=1 that is one CTA per 128-token page,
so each program does a single small `[8,128]x[128,128]` dot and exits.

First the launch grids, to show the cap only acts where pages are plentiful:

| B | S | pages | shipped grid | cap 32 grid | cap 16 grid |
|---|---|---|---|---|---|
| 1 | 4096 | 32 | (1,32,1) | (1,32,1) unchanged | (1,16,1) |
| 1 | 16384 | 128 | (1,128,1) | (1,32,1) | (1,16,1) |

Equivalence through the public API (`msa002_decode_cap.py`): the FP32 score
tensor and the selected `topk_idx` were **bit-exact** for shipped vs cap 32 at
S=4096 and S=16384; the full decode output was also bit-exact for caps 32 and
16 at both lengths. No padding/set comparison was needed — the tensors are
identical.

Timing (interleaved 3 rounds x 20, plus a 30-sample index-stage run):

| S | stage | shipped | cap 32 | cap 16 | best speedup |
|---|---|---|---|---|---|
| 4096 | index stage | 0.1201 | 0.1201 | 0.1193 | 1.006x (no-op, already 32) |
| 4096 | whole call | 0.2036 | 0.2078 | 0.2012 | 1.012x (noise) |
| 16384 | index stage | 0.1642 | 0.1366 | 0.1349 | **1.202x / 1.218x** |
| 16384 | whole call | 0.2027 | 0.2003 | 0.2012 | 1.012x |

Score-kernel-only sweep (`msa002_chunks2.py`, 50 samples, direct kernel launch,
re-run after the device fault): S=16384 pages=128 -> 128 chunks 0.1035 ms,
64 chunks 0.0778, 32 chunks 0.0739, 16 chunks 0.0779; best 32 chunks =
**1.40x on the score kernel**, all bit-exact.

Honest reading: the score kernel really is ~1.4x faster with 32 chunks and the
index stage is ~1.2x faster, but the **whole decode call only moves ~1%**,
because at batch 1 a decode call is ~45% fixed per-call overhead (section 4.3)
and the attention stage is unchanged. This is a real but small end-to-end win;
it is not the primary bottleneck.

## 8. Concurrent load / overlap

- GLA-006 ran on GCU 0 during the phase-1/2 window (`10:05`-`11:00` UTC),
  including Triton `llc`/`gcu-compiler-opt` processes.
- **10:59-11:12 UTC was quiet:** GLA-006 finished, host load dropped, GCU 1 used
  memory was 0 MiB at preflight, and the 5-round A/B in section 7.3b was run in
  that window. Its ratios agreed with the overlapping-window ratios to <0.01.
- Absolute latencies still refer to this 2-multi-processor container and to a
  742 GB shared host; treat them as relative, not as a hardware peak.
- A hard interrupt happened at 10:57:50 UTC: a SIP exception on GCU 1 during an
  exploratory decode script (`topsErrorSharedObjectInitFailed`, KMD "Sip
  exception"). The device disappeared from `efsmi -L` for ~60 s, then
  re-enumerated on its own without any privileged action. No reboot, no driver
  reload, no sudo. The shipped decode path was re-verified afterwards
  (`post_fault_decode.log`: 1x1x16384 0.1981 ms, same as before), and the
  group-16 A/B reproduced to 0.001 ms (`phase3_postfault_ab.log`). Evidence is
  preserved in `phase3_device_fault.log` and `phase3_ab_decode.log`.

  Root cause is **not** established. The failing frame was the `load_binary`
  for `_merge_topk_attn_out_kernel_enflame` in my own ad-hoc script, on a path
  (S=4096 decode, qlen=1) that had already run successfully many times. The
  same script shape faulted a second time at S=16384 (this time with the
  kernel's printf buffer reported corrupted: `async_printf.cc: printf_display
  detected the buffer is corrupted`), so the ad-hoc script's launch sequence is
  a plausible but unproven contributor; I could not reproduce the fault with
  the shipped public API. Two candidate explanations remain open: a driver
  robustness bug on this firmware, or a bad launch configuration in my
  throwaway script. Do not attribute it to the MSA kernels themselves — no
  fault occurred in any repo test, benchmark, or A/B run after the switches
  were exercised through the public API only.

## 11. Remaining work

1. **Widen the gate matrix before enabling by default** (highest value). The
   quiet-window win is solid for `total_q` 512-1023 with a small page pool, but
   only 6 shapes were covered. Sweep `total_q` 512-1023 x S in
   {1024, 2048, 4096, 8192} x topk in {4, 8, 16} x batch in {1, 2, 4, 8}, with
   the reference check on every cell, and confirm no cell regresses. Q=128
   already regresses with group 16 (0.88x), so the `total_q >= 512` floor must
   stay.
2. **Decode chunk cap: decide the threshold.** 32 chunks is best at S=16384 and
   a no-op at S=4096 (already 32). Needs a sweep over page counts 32-512 to pick
   the cap as a function of `max_block`, and must respect the `grid.y <= 255`
   limit — which is why the shipped code caps at 128 and why `num_kv_chunks=512`
   fails with `OutOfResources`.
3. **Decode identity path** (`max_block <= topk`, e.g. S=2048) was timed but not
   reference-checked; add it to the correctness matrix.
4. **Device-level attribution**: try an ncu/toolkit path or a newer torch_gcu if
   available; `torch.profiler` cannot attribute GCU kernels in this image, so
   per-kernel device time remains unmeasured and all conclusions rest on
   synchronized stage timing plus launch accounting.
5. **Compile-time cost**: first-call compile is 2.6 s for score on both stages.
   If production sees shape churn, a warmup/compile-cache check is worth adding
   (not investigated here).
6. **Fault follow-up**: reproduce or exonerate the SIP exception with a
   minimal script, and check whether the installed torch_gcu/firmware has a
   known issue. Until then, avoid ad-hoc direct-kernel launches on this box and
   drive experiments through the public API.
