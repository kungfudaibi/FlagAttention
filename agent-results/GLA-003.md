# GLA-003: FP16 64x64 GLA forward+backward on Enflame

## Verdict (short)
At baseline `4f437de`, the remaining B1,T512,H4,D64 FP16 forward+backward cost
is dominated by one backward stage: `chunk_gla_bwd_dqk_intra` at ~0.77 ms of a
~1.9 ms summed stage budget (whole forward ~0.45 ms). FP16 was forced onto a
scalar `exp(g_i-g_j)` loop there, while BF16 already used a centered
triangular block-dot. Allowing that block-dot for FP16 **only at K=64** cuts
the stage to ~0.28 ms (2.7x, reproduced 3/3 rounds) with no NaN/Inf and
<=1.6e-5 relative RMS versus the exact baseline commit. The full
forward+backward A/B at T512 improved by ~12% in median-of-round-medians but
the host is very noisy, so the end-to-end gain is directional, not a clean
>5% proof; the stage-level result is the solid evidence. T64 is flat within
noise. Code is worth review as a small, separately revertible change.

## Timing口径 (what the numbers mean, and what they do not)
Host wall time around explicitly `torch.gcu.synchronize()`-bounded calls, after
warmup: launch + execution + Python overhead, **not** device-event kernel time.
Each process reports per-call samples; we report each round's median and the
median of round medians. Cold compile is recorded separately and is **never**
used to infer speedup (first forward call includes ~2.7 s of Triton compile;
one T64 candidate process had a 4993 ms first backward call, a compile
outlier, kept in `agent-results/raw/ab_T64.jsonl`).

`PARALLEL_BWD_STATE_ENABLED` was not touched or toggled in any measurement
here. Baseline and candidate are the same code except for the one dispatch
line below, run as alternating processes.

## Baseline stage split, B1 T512 H4 K=V=64 FP16
Medians of 3 alternating rounds x 10 samples each, script
`agent-results/prof_stages.py` (stage calls under `torch.no_grad`):

| stage | baseline ms | candidate ms |
|---|---:|---:|
| `chunk_gla_fwd` (whole forward) | 0.447 | 0.448 |
| of which `chunk_fwd_h` | 0.160 | 0.158 |
| `chunk_bwd_dh` (states_in_fp32) | 0.205 | 0.204 |
| `chunk_gla_bwd_dv` | 0.130 | 0.134 |
| `chunk_gla_bwd_dA` | 0.116 | 0.117 |
| **`chunk_gla_bwd_dqk_intra`** | **0.773** | **0.282** |
| `chunk_gla_bwd_dqkg` | 0.171 | 0.175 |

Before the change the dominant backward cost is the dq/dk intra kernel
(~41% of the summed stages), not the parallel-state path added by PR #42.
`chunk_bwd_dh` and the forward scan are already small at this shape, so the
remaining headroom was in the intra backward, not in state handling.

## Change (one focused edit)
`src/flag_attn/runtime/backend/_enflame/FLA/gla/chunk_gla.py`,
`chunk_gla_bwd_dqk_intra` dispatch only:

    -        use_block_dot = q.dtype != torch.float16
    +        use_block_dot = q.dtype != torch.float16 or K == 64

The block-dot branch already exists; its operands are centered on a mid-block
reference gate, so `exp(g-g_ref) * exp(g_ref-g)` stays bounded instead of
forming huge `exp(-g)` times tiny `exp(g)`. FP16 at K=128/256 keeps the scalar
recurrence; BF16 is unchanged (`use_block_dot=True` before and after). The
diagonal sub-block is still masked to lower-triangular and accumulated in FP32
with `input_precision="ieee"`.

## End-to-end A/B, same harness, alternating processes (T512 FP16 64x64)
`agent-results/prof.py`: forward+backward step, 30 timed calls after 10
warmups per process, 3 alternating rounds (raw
`agent-results/raw/ab3_T512.jsonl`):

| round | baseline median ms | candidate median ms |
|---|---:|---:|
| 1 | 7.132 | 6.667 |
| 2 | 7.560 | 7.533 |
| 3 | 12.311 | 5.108 |
| median of round medians | **7.560** | **6.667** |

That is ~12% better, but round 2 is essentially tied and round 3's baseline
outlier drives much of the difference; per-call spread inside a round is
several ms on this shared host. An earlier 5-round x 20-sample run
(`agent-results/raw/ab2_T512.jsonl`) gave 11.992 -> 8.032 ms medians with
equally large round-to-round swings, and an initial 5-sample run
(`agent-results/raw/ab_T512.jsonl`) even had candidate slower in two rounds.
We therefore do **not** claim a validated >5% end-to-end speedup; the claim we
stand behind is the stage-level 0.773 -> 0.282 ms (2.7x) reproduced in every
alternating round.

T64 FP16 64x64, same method (`agent-results/raw/ab3_T64.jsonl`):
baseline medians 3.637 / 3.152 / 2.946, candidate 3.206 / 3.202 / 3.240,
median-of-medians 3.152 -> 3.206 (+1.7%). That is within noise and not a
measurable regression; the changed kernel is a small part of T64 cost.

## Passed / unverified scope
Passed: FP16 K=V=64, BT=BS=64, no cu_seqlens, HQ==H, T=63/64/512,
gate_logit_normalizer 0.1/1.0/10.0 spot checks, on `gcu:0`.
Unverified: FP16 at K=V=64 with T>512, GQA (HQ!=H), varlen/cu_seqlens,
state_v_first, split_size!=chunk_size, g_gamma/gv set, non-64 chunk sizes,
multi-device; FP16 K or V != 64 deliberately keeps the old scalar path and was
not re-benchmarked; BF16 was not re-timed here (its dispatch is unchanged).

## Limitations
- Single host/GCU generation; wall-clock numbers are not portable.
- The container exposes both GCUs and cannot mask GCU 1 via
  `GCU_VISIBLE_DEVICES`; all allocations used `gcu:0`.
- The end-to-end A/B is noise-limited; only the stage-level measurement is
  clean. Cold-compile numbers are excluded from all speedup claims.
- Prior GLA-002 report's 8.665 -> 2.255 ms A/B was for the *backward state
  gate*, not this change; its toggle-based sweep is not reused here.

## Recommendation
Worth review as a separate, revertible commit on the task branch: one dispatch
predicate, no new kernel, BF16 untouched, FP16 wide-K untouched, numerically
within tolerance against the exact baseline commit, and a reproducible 2.7x on
the dominant backward stage at T512. It should not be folded into PR #42
without a cleaner end-to-end measurement on a quiet host.
